# More detailed cards and Cross-Workspace collab

## Problem

A card holds only a title, so the task an agent should work on lives in the user's head or in a first message typed by hand, and an agent in one workspace can't hand work over to another workspace: `board` only sees the calling card's own workspace. After this ships, a card can carry a markdown description, entered in a new New card dialog, edited later, or set by an agent, and every fresh agent start in that card is told to read it and ask the user whether to start on it. A local card's `board` can list every workspace and create, rename, move and describe cards in any of them, including a card that gets its own worktree on first open, so an agent can port the current work to another workspace. Kanban columns can also be sorted recently opened first, and the board card's tooltip shows when the card was created and last opened.

## Domain decisions

- **D1 – Description:** a card has an optional `description`: plain markdown text, at most 100,000 characters (longer is refused, never cut), trimmed of trailing whitespace; an empty one is the same as none (the key absent). It is saved in `bikube-state.json` and synced through the Sync folder like the title (`toSyncBoard` / `applySyncBoard`, last writer wins as for titles). Bikube never renders it as markdown: it is shown and edited as text. *Why:* the developer chose a synced text field over a per-card file (round 1 Q1); a cap keeps the state and sync files and `board` requests bounded.
- **D2 – The first prompt:** on every **fresh** agent start of a card that has a description, the start line passes the agent a fixed first prompt, the constant text `This card has a task description. Read it with: board description .  Then summarise it in a few lines and ask me whether to start on it. Do not start working on it until I say so.` (single-quoted in the typed line; it holds no single quote, backslash or `$`, so it is the same in sh, bash, zsh and fish). Nothing from the card is put in the typed line. Fresh means: Claude Code before `claudeStarted` (only on the `--session-id <id>` branch: `claude --settings "$BIKUBE_CLAUDE_SETTINGS" --session-id <id> '<prompt>' || claude --settings "$BIKUBE_CLAUDE_SETTINGS" --resume <id>`), and a preset not yet in `startedAgents` (`codex '<prompt>'`, `gemini -i '<prompt>'`, `opencode --prompt '<prompt>'`, `pi '<prompt>'`). So it comes at a card's first start, after a newly picked agent, and after Move to own worktree… / Remove worktree… (new session); never on a resume, a `/clear` inside the agent, a Custom command or a plain shell, and never because the description was added or edited later. A card without a description starts exactly as today. *Why:* round 1 Q2 and Q9: the agent reads the task itself and asks first rather than starting; a fixed line keeps #21 D8 (no card text typed into a shell).
- **D3 – New card dialog:** `+ New card` at the end of a Kanban column, the grid view's New card button and the palette's New card open a **New card** dialog instead of the inline form (which is removed): **Title** (optional, placeholder `Terminal N` as today, focused), **Description** (multi-line, optional, the D1 cap shown as a counter only past 90,000 characters), **Agent** (the startup select with its Custom… command field, preset to the workspace default, agents not installed disabled as today), **Own worktree** with its branch (shown only for a local workspace inside a git repository, as today: the worktree is made by main before the card is created, with the workspace's Worktree setup queued). The dialog names the column it adds to (`Add to <column>`; the grid's goes to the first column). **Create** (also Enter in the title and Mod+Enter anywhere in the dialog) creates the card at the bottom of that column and opens it, which starts it, as today; Esc and **Cancel** close it with nothing created; a worktree failure keeps the dialog open with git's error, as today. *Why:* round 1 Q3; a description needs room the inline form doesn't have.
- **D4 – Seeing and editing a description:** a board card with a description shows a small document icon on its title row (Kanban and grid), whose tooltip is its first 5 lines (each cut at 120 characters, `…` when there is more). **Edit description…** in the card's ⋯ menu (board, grid and the open card's menu) opens a dialog with the same field and counter: Save stores it (empty removes it), Cancel and Esc change nothing. Editing never types anything into a running card. *Why:* round 1 Q4.
- **D5 – `board description` and `board describe`:** `board description <card>` prints the card's description followed by one newline, or nothing (exit 0) when it has none. `board describe <card> <file>` replaces it with the file's contents (`-` reads stdin); an empty file removes it; over 100,000 characters, an unreadable file or not UTF-8 text is refused (exit 1, nothing changed). The CLI reads the file, so the request carries the text: the request line limit rises from 8 KiB to 512 KiB. Both are in `board help` and in Bikube's Claude instruction. SSH cards' remote client gains `description` for their own card (`.` or its id) so D2's prompt works there; it does not take `describe` (D9). *Why:* round 1 Q4; an agent reads and writes descriptions through the same channel it already uses.
- **D6 – Workspaces from `board`:** `board workspaces [--json]` lists every workspace in sidebar order: its id, name, `local` or `ssh <host>`, directory, and `*` (JSON `"current": true`) for the calling card's. `--workspace <name or id>` selects the workspace for `list`, `create`, `rename`, `move`, `status`, `description` and `describe`: an exact id, else a name matched case-insensitively; no match → `no workspace named <x>`, more than one → `<n> workspaces are named <x>; use its id` (both exit 1). *Why:* round 1 Q5; names are what the user says, ids are unambiguous.
- **D7 – Naming cards and columns across workspaces:** a card's id names that card in any workspace; `.` is the calling card; a card title and a column title resolve only in the calling workspace, or in the one `--workspace` names. `board move <card> <column>` moves within the card's own workspace (never between workspaces): the column is resolved in the card's workspace. `activity`, `session`, `setup` and `usage` stay as today (the calling workspace). `board list` gains each card's `description` flag (`hasDescription` in JSON, `· description` in text). *Why:* round 2 Q1; ids are global so an agent can act on what it just created elsewhere.
- **D8 – `board create`:** `board create [--workspace <w>] [--agent <a>] [--description-file <file>|-] [--worktree [--branch <name>]] <column> <title>` adds a card at the bottom of the column, not started, and prints `<id> <workspace name>`. `--agent` is `claude`, `codex`, `gemini`, `opencode`, `pi` or `shell`; without it the card gets the calling card's agent (Claude Code from a Claude Code card), or the target workspace's default startup when the calling card runs a Custom command or a plain shell. The description follows D1 and D5's rules. A card is created in the target workspace's folder with its host, as a card made there by hand. *Why:* round 1 Q7.
- **D9 – Who reaches other workspaces:** only local cards' `board`. SSH cards keep their own card (their session sockets serve only it) and take `description` for it; `--workspace`, `workspaces`, `create`, `rename`, `describe` and an id of another card are refused there as today's usage error. *Why:* round 1 Q6.
- **D10 – A worktree on first open:** `--worktree` (with `--branch <name>`, else the branch `suggestBranch` derives from the title) is checked at create: the target must be a local workspace inside a git repository and the branch must pass `branchProblem` and not exist yet; otherwise `create` is refused with the reason (`<workspace> is an SSH workspace`, `<folder> is not in a git repository`, git's or the name's problem) and nothing is created. The card is created with `pendingWorktree: { branch }` in the workspace folder, shows a `Worktree on first open` pill, and its first open (by any path: click, palette, Open in new window, Next waiting card) makes the worktree as **Move to own worktree…** does (main creates it, the card's directory moves there, the Worktree setup is queued, a new agent session) before it starts; if that fails, the card stays pending, shows git's error in the card view with **Retry** and **Run in workspace folder** (which drops the pending worktree and starts it there). `pendingWorktree` is synced: whichever machine opens the card first makes it, then the worktree syncs as worktree cards do today. *Why:* round 1 Q8, round 2 Q2 and Q4; a worktree made at create time would need main to answer before the agent's command returns, and on a synced board only the opening machine should touch git.
- **D11 – New mark:** a card created by `board create` from a card in another workspace carries `unopened: true`, shown as a `New` pill on the board card (Kanban and grid) until its first open on any machine, which clears it (synced, one write). Cards created in the calling workspace, by hand or by a restart, get none. *Why:* round 2 Q3; the user is told without a notification.
- **D12 – Kanban sort:** a workspace has a `sort`: `manual` (default, the key absent) or `recent`, synced like `view`. It is set from any column's ⋯ menu (`Sort: Manual order` / `Sort: Recently opened first`, a radio pair applying to the whole board) and in the workspace's Edit dialog (hidden in Grid view, as the move rules are). Under `recent` each column shows its cards by the later of `createdAt` and this machine's `lastOpenedAt`, newest first, cards with neither after them in board order (the grid's rule, shared); dragging to another column, Move to and `board move` still change the column, but the stored order within a column is not changed by them and no drop indicator is shown inside the column; Alt+Up/Down do nothing; Alt+Left/Right still move between columns. Switching back to `manual` shows the stored board order unchanged. The Card display limit (fold) applies to the sorted order. The grid view is unchanged (already latest first). *Why:* round 3 Q1–Q3; `lastOpenedAt` stays unsynced so a click never writes the sync file.
- **D13 – Dates:** the board card's tooltip (Kanban and grid, on the card body, not its chips) reads `Created <date time> · Opened <relative time>`, e.g. `Created 27 Oct 2026, 14:05 · Opened 3 min ago`, in the system locale; `Opened never` when never opened on this machine; the `Created` part is left out for a card without `createdAt`. *Why:* round 3 Q4.
- **D14 – Claude instruction:** `LOCAL_CLAUDE_INSTRUCTION` (and `resources/bin/claude-instruction.txt`, kept equal by its test) gains two lines: a card may have a task description (`board description .`), and to port work to another workspace use `board workspaces`, then `board create --workspace <w> --description-file - <column> <title>` (with `--worktree` when the user asks for one), writing the description from what the user asks for. *Why:* the porting flow from the item description must be discoverable to Claude Code.

## Acceptance criteria

- **AC1 – New card dialog:** Given a local workspace with column `Todo`, when the user clicks `+ New card` under `Todo`, then a `New card` dialog opens with Title focused, a Description field, the Agent select on the workspace default and (in a git repository) Own worktree; typing `Fix login`, a description `# Goal\nFix the login bug`, picking a Custom command `:` and pressing Mod+Enter creates `Fix login` at the bottom of `Todo`, opens it and starts it, and `bikube-state.json` holds the description; Esc instead closes the dialog with no card. The grid's New card and the palette's New card open the same dialog.
- **AC2 – First prompt on a fresh start:** Given a Claude Code card with a description that never started, when it is opened, then the typed line is `claude --settings "$BIKUBE_CLAUDE_SETTINGS" --session-id <id> '<D2 prompt>' || claude --settings "$BIKUBE_CLAUDE_SETTINGS" --resume <id>` (the fake `claude` logs the prompt argument); after a Close and reopen (resume) the line holds no prompt; a Codex card with a description starts `codex '<prompt>'` then `codex resume --last || codex`; a card without a description starts as before.
- **AC3 – Edit description:** Given a card, when **Edit description…** in its ⋯ menu saves `Step one\nStep two`, then the board card shows the description icon whose tooltip reads `Step one` and `Step two`; saving it empty removes the icon and the `description` key; a running card's shell receives nothing.
- **AC4 – `board description` / `describe`:** Given a card with description `Hello 69`, when `board description .` runs in it, then it prints `Hello 69`; `printf 'New text' | board describe . -` replaces it (the icon tooltip reads `New text`); a 100,001-character file is refused with exit 1 and the description unchanged; a card with none prints nothing and exits 0.
- **AC5 – `board workspaces`:** Given workspaces `Alpha` (current) and `Beta`, when `board workspaces` runs in an `Alpha` card, then it prints both in sidebar order with their ids, `local`, directories and `*` on `Alpha`; `--json` gives the same with `"current": true` on `Alpha`.
- **AC6 – Create in another workspace:** Given that, when an `Alpha` Claude Code card runs `printf '# Port\nDo X' | board create --workspace beta --description-file - Todo 'Port X'`, then it prints `<id> Beta`; `Beta`'s `Todo` has `Port X` at the bottom, Stopped, Claude Code, with the description and a `New` pill; opening it removes the pill and starts Claude Code with D2's prompt.
- **AC7 – Acting on another workspace's cards:** Given `Port X` in `Beta` with id `<id>`, when an `Alpha` card runs `board rename <id> 'Port Y'`, `board move <id> Doing`, `board status <id> queued` and `board description <id>`, then each acts on `Beta`'s card; `board rename 'Port Y' Z` (a title) fails with `board: no card "Port Y" in this workspace` unless `--workspace Beta` is given; `board list --workspace Beta` lists `Beta`'s columns; `--workspace nope` exits 1 with `board: no workspace named nope`, and two workspaces named `Beta` give `board: 2 workspaces are named Beta; use its id`.
- **AC8 – Default agent:** Given a Codex card in `Alpha`, when it runs `board create --workspace Beta Todo T1`, then `T1` is a Codex card; from a Custom command card, `T1` gets `Beta`'s default startup; `--agent gemini` gives a Gemini CLI card.
- **AC9 – Worktree on first open:** Given `Beta` a local git repository, when `board create --workspace Beta --worktree --branch port-x Todo 'Port X'` runs, then the card shows `Worktree on first open` and no worktree or branch exists yet; opening it creates the worktree on `port-x`, the card shows the branch, runs in the worktree and the pill is gone. With `Beta` an SSH workspace, the same command exits 1 with `Beta is an SSH workspace`; with a folder outside git, `<folder> is not in a git repository`; with `--branch main` (exists), git's refusal; nothing is created in each case.
- **AC10 – Pending worktree across machines:** Given two instances sharing a Sync folder, when instance A creates a `--worktree` card, then instance B shows it with `Worktree on first open`; opening it on B makes the worktree on B, and A then shows it as a worktree card.
- **AC11 – SSH cards:** Given an SSH card with a description, when `board description .` runs in it, then it prints the description; `board workspaces`, `board create …` and `board describe . -` print the SSH usage with exit 2.
- **AC12 – Kanban sort:** Given a column with cards `A`, `B`, `C` (board order) where `B` was opened last and `C` before it, when the user picks `Sort: Recently opened first` in a column menu, then the column shows `B`, `C`, `A`, the workspace's state has `"sort":"recent"`, Alt+Up on `A` changes nothing, dragging `A` to another column moves it there, and picking `Sort: Manual order` shows `A`, `B`, `C` again; the Edit dialog shows the same choice; opening `A` puts it first.
- **AC13 – Dates tooltip:** Given a card created at a known time and opened once, when the pointer rests on the board card, then its tooltip reads `Created <that date and time> · Opened <n> min ago` (`just now` under a minute); a never-opened card's reads `· Opened never`.
- **AC14 – Request size:** Given a description of 100,000 characters (multi-byte included), when `board describe . <file>` runs, then it is stored whole and `board description .` prints it back unchanged.

## Data and migrations

- `Card` gains `description?: string` (saved, synced), `pendingWorktree?: { branch: string }` (saved, synced), `unopened?: true` (saved, synced). Each is absent when empty/false; older state and sync files simply lack them, and a file with a bad value drops that key only (the card is kept).
- `Workspace` gains `sort?: 'recent'` (absent = manual; saved, synced like `view`).
- `board` protocol: `MAX_REQUEST_LINE_BYTES` 8 KiB → 512 KiB; new commands `workspaces`, `description`, `describe`; a `workspace` field on the commands D6 lists; `create` gains `agent`, `description`, `worktree`, `branch`.
- No migration: existing cards have no description, no pending worktree, no `New` mark; existing workspaces stay `manual`.

## Out of scope

- Rendering descriptions as markdown, a side panel Task tab, attachments or images in a description.
- Moving a card between workspaces, or `board` from SSH cards reaching other cards or workspaces.
- Typing a description into an agent that already has a conversation (resume, or a description edited later); the user asks the agent to run `board description .`.
- A notification when a card is added to another workspace.
- Syncing `lastOpenedAt`; sorting the grid differently.
