# Project orchestrator

## Problem

Every workspace has a Default shell that is just another plain terminal, while the work of running the board (creating cards, starting agents, checking what they found, switching views) is done by hand or by whichever card's agent happens to be asked. After this ships, each local workspace has one **Orchestrator**: a terminal running an agent (Claude Code by default, chosen in Settings) that knows it orchestrates Bikube, resumes its conversation whenever it is opened, and can drive the board and the app: list and create cards in any workspace, start and open them, send them text, wait for them and read their replies, open terminals running a command, and run any command palette row. What it is told comes from one instruction file shipped with Bikube (updated with every release) plus the user's own text in Settings, so no orchestrator has to be re-taught. The Default shell is removed: New shell (Cmd+T) always opens a new temporary `Terminal N`.

Related: #80 (in review) adds a preference to `src/core/settings.ts` and touches `card-actions.ts`, `CardView.tsx` and `e2e/fake-claude.ts`; this item's edits there are additive (new preferences, a new branch in `startCard`) and must merge cleanly with it.

## Domain decisions

### The Default shell and New shell

- **D1 – No Default shell:** the Default shell (`default-shell:<workspace id>`, never stored) is removed everywhere: the Shells tab, the sidebar tree, the palette's Shells section, the waiting queue, notifications and `board`'s calling-terminal lookup. Nothing in a state or sync file names it, so no migration is needed; a `runIn`, kept output or anything else keyed by such an id is simply never found. A workspace with no named shells shows the Shells tab with a new empty line, `No shells yet.`, above its add button. *Why:* round 1 Q2; the Orchestrator takes its place as the workspace's built-in terminal.
- **D2 – New shell:** the `openShell` action (Cmd+T / Ctrl+Shift+T, the toolbar's and title bar's New terminal, the palette's `New shell`) always adds a new temporary `Terminal N` (the lowest free N in the workspace, #66) and opens it; temporary shells otherwise behave exactly as today (runtime only, removed when they stop, listed in the sidebar tree and palette, never in the Shells tab). *Why:* round 1 Q2.
- **D3 – Shells keep `board`:** what the Default shell could do with `board` (list, create and move named cards, set its own runtime `status`, `activity`, `session` and `usage`, feeding the Agent tab, #75 D3a) stays for every named and temporary shell. Tests that used the Default shell for a plain terminal use a temporary shell (`Terminal 1`) instead. *Why:* nothing a user relied on is lost with D1.

### The Orchestrator

- **D4 – One per local workspace:** every local workspace has exactly one Orchestrator, id `orchestrator:<workspace id>`, a card-shaped terminal (like a shell: not on the board, no column, opened at full size in the card view, splittable, openable in its own window) running in the workspace's folder. Its title is `Orchestrator`; where it stands alone (palette, its own window's title) `Orchestrator · <workspace name>`. SSH workspaces have none (D10). *Why:* round 1 Q1, Q9.
- **D5 – Where it shows:** an **Orchestrator** button in the workspace toolbar, left of Agent setup, with a `Tooltip` (name, `Opens the workspace's orchestrator agent`, the Open orchestrator shortcut) and a chevron menu holding **New conversation…**; its row first in the workspace's sidebar tree while it runs (Nested), and in Split's Agents section like any agent row (#79); a palette row `Open orchestrator` in the actions and `Orchestrator: New conversation` while one exists; never in the Shells tab. *Why:* round 1 Q1, Q7.
- **D6 – Open orchestrator shortcut:** a new configurable action `openOrchestrator`, label `Open orchestrator`, default **Alt+Cmd+O** on macOS and **Ctrl+Alt+O** elsewhere, recordable and resettable in Settings > Shortcuts, working from a focused terminal (the shell gets none of the keys). It opens the active workspace's Orchestrator, starting it when it isn't running. *Why:* round 1 Q10 asked for Cmd+Shift+O / Ctrl+Shift+O, but both are already Open in new window's defaults (#53); Alt+Cmd+O / Ctrl+Alt+O are free on both platforms. The developer can change this at approval.
- **D7 – Agent setting:** Settings > Agents gains **Orchestrator agent**, one app-wide select: Claude Code (default), Codex, Gemini CLI, OpenCode, Pi, Custom command (with its command field), agents not installed disabled `(not installed)` as in the New card dialog. Saved as `orchestratorStartup` in `bikube-settings.json` only when not Claude Code. A change applies at the Orchestrator's next start; a running one keeps its agent. *Why:* round 1 Q3.
- **D8 – Its conversation:** a workspace stores `orchestrator: { agentSessionId, claudeStarted, startedAgents }` (absent until its first start), saved in `bikube-state.json` and synced through the Sync folder like a card's, so it resumes as a card does (`--session-id` the first time, `--resume` after; a preset's resume command once in `startedAgents`), on this machine or another where the agent can (#13). `board session .` from it updates `agentSessionId` as for a card. *Why:* round 1 Q6.
- **D9 – Signals like a card:** it has a status line (`board status .`), activity (`board activity .`, set by Claude Code's hooks), joins the waiting queue (sidebar dot, Next waiting card, notifications), the Split sidebar's Agents section, the Agent tab (its folder and `agentSessionId`, as a local Claude Code card), and kept output (#46) as a card's main pane does (its save keyed by its id, kept at launch while its workspace exists). Usage from `board usage .` shows in the Agent tab's header. It has no board card, so no chips, pills or move rules. *Why:* round 1 Q8.
- **D10 – SSH workspaces:** the toolbar button is shown disabled with the tooltip line `The orchestrator needs a local workspace`; the palette rows are absent and the shortcut does nothing in an SSH workspace. *Why:* round 1 Q9.
- **D11 – New conversation:** **New conversation…** (the button's menu, the palette row) asks `Start a new orchestrator conversation? The current one is kept by <agent> but the orchestrator won't resume it.` with Cancel and **New conversation**; confirming stops it if it runs (as Close does, with no further confirmation), gives it a new `agentSessionId`, clears `claudeStarted`, `startedAgents` and its kept output, then opens and starts it. *Why:* round 1 Q7.

### Its instructions

- **D12 – One shipped guide:** Bikube ships the orchestrator's instructions as `resources/bin/orchestrator-instruction.txt`, generated from a constant in `src/core` (kept equal by a test, as `claude-instruction.txt` is). It tells the agent: it is the Orchestrator of Bikube workspace `<name>` in `<folder>`; what Bikube's cards, columns, workspaces, worktrees and shells are; every `board` command it may run (the ones below and today's), each with one example; and how to do the item's examples (switch workspace or open Agent setup through `board palette run`, a dev server through `board terminal --show`, a reviewer through `board create` + `board start` + `board wait` + `board reply`, an issue's worktree card through `board create --worktree --description-file -` + `board start`). *Why:* round 1 Q4: one file updated by every release reaches every orchestrator at its next start or resume.
- **D13 – `board guide`:** a new command, run in the Orchestrator only (D16), prints the guide with the workspace's name and folder filled in, followed, when Settings' **Your orchestrator instructions** (D14) is not empty, by a line `## Your instructions` and that text. *Why:* one place every agent reads, whatever starts it.
- **D14 – The user's text:** Settings > Agents gains **Your orchestrator instructions**, a multi-line text field (at most 20,000 characters, trailing whitespace trimmed), saved as `orchestratorInstructions` only when not empty; read by `board guide` at each run, so an edit reaches every orchestrator at its next start, resume or `/clear`. *Why:* round 1 Q4.
- **D15 – Delivery:** the Orchestrator's shell gets `BIKUBE_ORCHESTRATOR=1`. Claude Code: Bikube's SessionStart hook prints `board guide`'s output in place of `claude-instruction.txt` when that variable is set (every start, resume, `/clear` and compact; still nothing with `BIKUBE_CLAUDE_STATUS=0`). A preset (Codex, Gemini CLI, OpenCode, Pi) on a fresh start gets the first prompt `You are this Bikube workspace's orchestrator. Run: board guide  Read it, then say in one line that you are ready.` the way #69 D2 passes its prompt; a resume gets none (the conversation already has it). A Custom command gets nothing typed; the user may run `board guide` themselves. *Why:* round 1 Q4; Claude Code re-reads it on every session start, the presets only when a conversation begins.

### Driving the board and the app

- **D16 – Only the Orchestrator:** before each Orchestrator session (its main pane and each extra pane) main listens on its own socket `<userData>/board/o-<16 hex>.sock` (0600 in the private `board` directory, closed when the session exits and on quit, leftovers removed at launch, as #25's session sockets) and gives it as `BIKUBE_SOCKET` with `BIKUBE_CARD_ID` the Orchestrator's id. Requests on that socket must name that id; they may run every command. The shared `board.sock` refuses the orchestrator-only commands (`guide`, `start`, `open`, `send`, `wait`, `reply`, `terminal`, `palette`) with `board: only the orchestrator can do that` (exit 1), and refuses any request naming an Orchestrator's id with `board: invalid request`, so no other process can act as it. The Orchestrator also runs every existing command as a local card does (`--workspace`, ids across workspaces, `board create` with the target workspace's default agent since it has none to pass on, #69 D8). *Why:* round 2 Q2: main tells the Orchestrator apart by the socket it was given, which `BIKUBE_CARD_ID` alone can't prove.
- **D17 – `board start` and `board open`:** `board start <card>` starts a stopped card (by id in any workspace, by title in the active workspace or `--workspace`'s) in the background, exactly as opening it would (its startup line, a pending worktree made first, #69 D10; it never changes the view and leaves the `New` pill); a running card prints `<title> is already running` (exit 0). `board open <card>` also shows it: makes its workspace active and opens the card at full size (in its own window if it has one), clearing `New` as any open does. Both refuse a card whose start fails with its reason (exit 1). *Why:* round 2 Q3, Q8: act at once, as asked.
- **D18 – Orchestrated cards start working:** a card created by the Orchestrator's `board create` carries `orchestrated: true` (saved, synced). On its fresh agent start with a description (#69 D2's rule for when), the first prompt is `This card has a task description. Read it with: board description .  Then start working on it.` instead of #69's ask-first prompt, whoever opens or starts it. *Why:* round 2 Q9: the developer wants a card the Orchestrator sets up to start without asking.
- **D19 – `board send`:** `board send <card> <text>` (`-` reads stdin; at most 100,000 characters; control characters other than newline and tab removed) types the text into a running card's main pane as one paste (bracketed when the program asked for bracketed paste, as xterm's paste does), then Enter (CR) 50 ms later. A card that isn't running is refused with `board: "<title>" is not running` (exit 1). It sets no activity and clears none. *Why:* round 2 Q4.
- **D20 – `board wait`:** `board wait <card> [--timeout <s>]` (default 600, 1 to 3600) returns as soon as the card is stopped (prints `stopped`), or its activity is `waiting` (prints `waiting`) or `question` (prints `question`), checked at once and then on each change; while it is `working` or has no activity it keeps waiting. Exit 0 for those, exit 1 with `board: timed out after <s> s` at the timeout. The CLI waits for the reply up to the timeout plus 5 s instead of #9's 5 s. *Why:* round 2 Q4; Claude Code's Stop hook sets `waiting` when its turn ends, so this is "the agent is done or needs someone".
- **D21 – `board reply`:** `board reply <card>` prints the main agent's last assistant text message from a local Claude Code card's transcript (`<home>/.claude/projects/<folder>/<session>.jsonl`, read by main as the Agent tab reads it, #75), its text blocks joined by blank lines, at most 100,000 characters (the end kept, `…` first when cut). Refused with `board: "<title>" is not a Claude Code card` or `board: "<title>" has no reply yet` (exit 1). *Why:* round 2 Q4.
- **D22 – `board terminal`:** `board terminal [--workspace <w>] [--show] <command>` adds a temporary `Terminal N` to the workspace (the active one, else `--workspace`'s; an SSH workspace's runs over SSH as its temporary shells do) whose startup types `<command>` (one line, at most 8 KiB, as a named shell's command), starts it, and prints `<name> <id>`; with `--show` it is also opened (workspace made active). It stays until its shell stops, as any temporary shell. *Why:* round 2 Q5.
- **D23 – `board palette`:** `board palette list` prints, one per line, the label of every action row the palette would show now for the user's current view (D2's sections, #40), minus rows that act on the open card or pane (Back, Split right, Split down, Close pane, Close card, Find, Copy command output, Move to …, Zoom pane, Next pane, Previous pane, Equalize panes, Rename card, Open in new window, Edit description…) and minus card and shell rows (`board open` covers those). `board palette run <label>` runs the row whose label matches case-insensitively after trimming, exactly as picking it would (switching workspace, Agent setup, themes, views, Sidebar layout, New card's dialog, Settings…), and prints nothing; no match → `board: no palette row "<label>"` (exit 1). It acts at once even when the user looks elsewhere. *Why:* round 2 Q6, Q7, Q8.
- **D24 – Help:** `board help` lists the orchestrator-only commands under `Orchestrator only:` in every terminal; the SSH client's usage is unchanged. *Why:* other agents learn they exist without being able to run them.

## Acceptance criteria

- **AC1 – New shell is always a terminal:** Given a workspace with no running terminals, when the user presses New shell, then `Terminal 1` opens at full size; pressing it again opens `Terminal 2`; the Shells tab lists no Default shell (with no named shells it reads `No shells yet.`), and neither the sidebar tree nor the palette has a `Default shell` row.
- **AC2 – Shells keep `board`:** Given `Terminal 1` open, when `board list` and `board status . building` run in it, then the board is listed and its Shells/sidebar row reads `building`.
- **AC3 – Open the orchestrator:** Given a local workspace `Proj` and a fake `claude`, when the user clicks the toolbar's **Orchestrator** button, then the card view shows `Orchestrator`, the typed line is `claude --settings "$BIKUBE_CLAUDE_SETTINGS" --session-id <uuid>`, its row is first in `Proj`'s sidebar tree, the shell's environment has `BIKUBE_ORCHESTRATOR=1`, and `bikube-state.json` has `Proj`'s `orchestrator.agentSessionId` equal to `<uuid>`. Alt+Cmd+O (Ctrl+Alt+O off macOS) and the palette's `Open orchestrator` open the same view.
- **AC4 – Resume:** Given the Orchestrator started once with session `<uuid>` and `claudeStarted`, when it is closed and opened again, and again after a restart, then its line is `claude --settings "$BIKUBE_CLAUDE_SETTINGS" --resume <uuid>`, and its kept output shows above the separator.
- **AC5 – Agent setting:** Given Settings > Agents' Orchestrator agent set to Codex with the fake `codex`, when a new workspace's Orchestrator opens, then its line is `codex '<D15 prompt>'`; reopened after Close, `codex resume --last || codex`; `bikube-settings.json` holds `orchestratorStartup` for Codex and none for Claude Code.
- **AC6 – Instructions:** Given **Your orchestrator instructions** set to `Always use worktrees.`, when `board guide` runs in the Orchestrator of `Proj` in `/x/proj`, then it prints the shipped guide naming `Proj` and `/x/proj`, then `## Your instructions` and `Always use worktrees.`; the fake `claude`'s SessionStart hook output (run with `BIKUBE_ORCHESTRATOR=1`) equals that text; with the field empty there is no `## Your instructions`.
- **AC7 – Only the orchestrator:** Given a plain card and `Terminal 1`, when `board guide`, `board start X`, `board palette list` run in either, then each prints `board: only the orchestrator can do that` and exits 1; a request on `board.sock` naming `orchestrator:<id>` is refused with `board: invalid request`.
- **AC8 – Start and open:** Given a Stopped card `Review` in workspace `B` while `A`'s Orchestrator is open, when it runs `board start <Review id>`, then `Review` becomes Running and the view still shows the Orchestrator; `board start <id>` again prints `Review is already running`; `board open <id>` makes `B` active and shows `Review` at full size.
- **AC9 – Orchestrated first prompt:** Given the Orchestrator runs `printf 'Review the branch' | board create --description-file - Todo Review`, when `board start Review` runs, then the fake `claude` logs the prompt `This card has a task description. Read it with: board description .  Then start working on it.`; a card made by hand with a description still gets #69's ask-first prompt.
- **AC10 – Send, wait and reply:** Given a running fake-`claude` card `Review` (its fixture transcript ending with an assistant message `Found 2 issues.`), when the Orchestrator runs `board send Review 'go on'`, then the card's main pane receives `go on` then Enter; `board wait Review --timeout 5` after `board activity <Review id> working` then `waiting` (typed in the card) prints `waiting` and exits 0; with no change it prints `board: timed out after 5 s` after about 5 s and exits 1; `board reply Review` prints `Found 2 issues.`; for a plain card it prints `board: "<title>" is not a Claude Code card`.
- **AC11 – Terminal:** Given workspace `A`'s Orchestrator, when it runs `board terminal 'printf ready'`, then it prints `Terminal 1 <id>`, the sidebar lists `Terminal 1` running with `ready` in its output, and the view is unchanged; `board terminal --show 'exec sleep 60'` opens `Terminal 2`.
- **AC12 – Palette:** Given workspaces `A` (active) and `B`, when the Orchestrator runs `board palette list`, then the output contains `Agent setup`, `Switch to workspace B` and `Settings`, and none of `Close card`, `Split right`, `Back to board`; `board palette run 'switch to workspace b'` makes `B` active; `board palette run 'Agent setup'` shows `B`'s Agent setup; `board palette run nope` exits 1 with `board: no palette row "nope"`.
- **AC13 – New conversation:** Given the Orchestrator ran with session `<u1>`, when the user picks **New conversation…** and confirms, then it restarts with `--session-id <u2>` (`<u2>` ≠ `<u1>`), no kept output above it, and the state file holds `<u2>`; Cancel changes nothing.
- **AC14 – SSH workspace:** Given an SSH workspace, then its toolbar's Orchestrator button is disabled with the tooltip line `The orchestrator needs a local workspace`, the palette has no orchestrator rows and Alt+Cmd+O (Ctrl+Alt+O) does nothing.
- **AC15 – Signals and sync:** Given the Orchestrator running, when `board activity . waiting` runs in it with the main window looking elsewhere, then the sidebar marks it, Next waiting card opens it, and Split's Agents lists it under Needs you; the Agent tab shows its conversation from its transcript; with two instances on one Sync folder, B's state holds A's `orchestrator.agentSessionId` and B's Orchestrator resumes it.
- **AC16 – Shortcut setting:** Given Settings > Shortcuts, then `Open orchestrator` shows its default, can be recorded (saved in `shortcuts`) and Reset.

## Stack changes

None.

## Data and migrations

- `Workspace` gains `orchestrator?: { agentSessionId: string; claudeStarted: boolean; startedAgents: string[] }`, saved and synced (last writer wins, as a card's fields); absent until the first start; a bad value drops only the key.
- `Card` gains `orchestrated?: true`, saved and synced; absent otherwise.
- `bikube-settings.json` gains `orchestratorStartup` (a startup command, absent for Claude Code), `orchestratorInstructions` (absent when empty) and an `openOrchestrator` entry in `shortcuts` when recorded.
- Nothing stored names the Default shell, so its removal migrates nothing.

## Out of scope

- An Orchestrator for SSH workspaces, or one per app instead of per workspace.
- A per-workspace agent or instruction text (app-wide only, round 1 Q3, Q4).
- `board output` (a card's terminal text; round 2 Q4 not picked), a one-off `--prompt` for `board start` (round 2 Q9).
- Palette rows acting on the open card or pane, and card/shell rows, from `board palette` (D23).
- `board send`, `wait`, `reply` for shells and terminals (cards only).
- Any confirmation or toast when the Orchestrator changes the view (round 2 Q8: act at once).
