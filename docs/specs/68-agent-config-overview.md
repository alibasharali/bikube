# Agent setup: a workspace's Claude Code configuration at a glance

## Problem

A workspace's Claude Code setup is spread over a dozen files in two places (the workspace folder's `.claude/`, `CLAUDE.md` and `.mcp.json`; the user's `~/.claude/` and `~/.claude.json`) plus installed plugins and Bikube's own hooks, so seeing which skills, subagents, commands, hooks, MCP servers, plugins, memory files and permissions a card's Claude Code gets means opening each file by hand, or starting Claude Code and using `/plugin`, `/mcp`, `/memory`, `/config` and `/status` one by one. After this ships, each local workspace has an **Agent setup** page, a full page in the main area opened from the board's title bar or the command palette, listing all of it by source, with warnings for broken files, stats of the workspace's Claude Code sessions, plugins and project MCP servers toggled on or off for the workspace, numeric and boolean settings changed in place, and every entry opened in the user's editor or revealed in the file manager.

Builds on the full-size card view and its per-workspace memory (#31 D19, `src/core/view-memory.ts`), the sidebar tree (`src/core/open-terminals.ts`, `WorkspaceTerminals.tsx`), the command palette (#40, `src/core/palette.ts`), the side panel's Files tab (#55: Settings > Editor, `src/core/editor.ts`'s `openFile`, its focus-based refresh and `src/renderer/src/window-focus.ts`), the installed-agents check through the login shell (`src/core/installed-agents.ts`), Bikube's Claude Code settings file (#31 D14, `src/core/claude-hooks.ts`, `resources/bin/claude-settings.json`) and #50's transcript reading (`src/core/claude-usage.ts`: the token counts and their deduplication; no cost).

## Domain decisions

### Placement and navigation

- **D1 – A page in the main area:** Agent setup is a third kind of view in the main area, beside a workspace's board and an open card or shell: it fills the main area (no side panel beside it) for the active workspace. *Why:* developer's answer (round 1 Q1): a full window, like an open card.
- **D2 – Opening it:** an icon button in the title bar while the active workspace shows its board (Kanban or Grid), left of the side panel toggle (lucide `Blocks` icon, `aria-label="Agent setup"`, tooltip `Agent setup`), and a palette action row **Agent setup** offered whenever a workspace is active and Agent setup isn't the view in front (from its board or from an open card or shell, which it replaces as a card opened from the palette would). No default shortcut, and it is not one of Settings' configurable shortcuts. Not in card windows. *Why:* developer's answers (round 1 Q1, round 2 Q2).
- **D3 – It acts like an open card:** while Agent setup is a workspace's view, its sidebar tree shows a row **Agent setup** (the `Blocks` icon, neutral colour, no status dot) nested under that workspace after its cards and shells, marked current while in front; clicking the row shows it. Back (the title bar's Back button, `Back to <workspace>`, and the Back shortcut) returns to the board and removes the row. The view is remembered per workspace for the run of the app exactly as an open card is (#31 D19): switching to another workspace and back shows it again; clicking the active workspace's own sidebar row shows its board and forgets it; opening a card or shell in that workspace replaces it; never saved or synced, so after a restart no workspace shows it. The title bar reads `<workspace> › Agent setup`. There is no row while it isn't open. *Why:* developer's answer (round 1 Q1: "acts as any other tab/session/terminal").
- **D4 – Its name:** `Agent setup` everywhere (title bar, sidebar row, palette row, button tooltip). *Why:* developer's answer (round 2 Q3).
- **D5 – Claude Code only:** every section is about Claude Code; the page's header reads `Agent setup` with a subtitle `Claude Code · <workspace folder>`. *Why:* developer's answer (round 1 Q2).
- **D6 – SSH workspaces:** for an SSH workspace the button and palette row are offered and the page shows only `Agent setup isn't available for SSH workspaces yet` (as the Files tab does); nothing is read or run. *Why:* developer's answer (round 1 Q9).
- **D7 – Layout:** a left section list inside the page, in four groups separated by a rule: **Overview**, **Status**, **Stats** | **Plugins**, **MCP servers** | **Skills**, **Agents**, **Commands**, **Hooks** | **Memory**, **Permissions**, **Config**. Each item shows its count of entries where it has one (Skills 12) and a warning dot when any of its entries has a warning (D24). The section shown is remembered per workspace for the run (Overview the first time). Above the list a search box (D25) and a **Refresh** button. Below 640 px of page width the list becomes a horizontal, scrolling strip of the same items above the content (the groups' rules kept as gaps); no horizontal page scroll. The page uses the app's tokens (`main.css`, app themes #64), the app font, and the look of Settings and the side panel: rows on `--panel`, chips for sources and states, toggle switches as in Settings. The section list is a `tablist` with `aria-orientation="vertical"` (horizontal below 640 px), Up/Down (Left/Right) moving between sections. *Why:* developer's answer (round 2 Q1); item: "look good and professional and follow the vibe of the rest of the app".

### Sources

- **D8 – What is read:** with `<folder>` the workspace's folder and `~` the user's home (main's `BIKUBE_HOME_DIR`, else the OS home, as sync does):
  - **Project:** `<folder>/.claude/settings.json`, `<folder>/.claude/settings.local.json`, `<folder>/.mcp.json`, `<folder>/.claude/skills/*/SKILL.md`, `<folder>/.claude/agents/**/*.md`, `<folder>/.claude/commands/**/*.md`, and memory (D17).
  - **User:** `~/.claude/settings.json`, `~/.claude.json` (its `mcpServers`, its `projects[<folder>].mcpServers` as **Local** scope, `oauthAccount`, and the preferences D21 names), `~/.claude/skills/*/SKILL.md`, `~/.claude/agents/**/*.md`, `~/.claude/commands/**/*.md`, `~/.claude/CLAUDE.md`.
  - **Plugins:** `~/.claude/plugins/installed_plugins.json` and `known_marketplaces.json`; for each installed plugin its `installPath`: `.claude-plugin/plugin.json` (name, version, description, author), `skills/*/SKILL.md`, `agents/**/*.md`, `commands/**/*.md`, `hooks/hooks.json`, `.mcp.json`. A plugin installed with scope `project` or `local` is listed only when its `projectPath` is `<folder>`.
  - **Bikube:** the hooks of Bikube's own Claude Code settings file (`claude-settings.json`, the one every Claude Code card gets with `--settings`), read-only.
  - Not managed (enterprise) policy settings. *Why:* developer's answer (round 1 Q3).
- **D9 – Entries carry their source:** every entry shows a source chip: `Project`, `Local` (settings.local.json, or `~/.claude.json`'s project entry), `User`, `Plugin <plugin name>` or `Bikube`. *Why:* item; round 1 Q3.
- **D10 – Settings precedence:** the effective value of a setting is the first file, in this order, that sets it: Bikube's file (only for `hooks`, which merge, below), `<folder>/.claude/settings.local.json`, `<folder>/.claude/settings.json`, `~/.claude/settings.json`. `hooks` and `permissions` rules merge across all sources (every source's entries apply); `enabledPlugins` merges key by key with the same precedence. Where the page says a value "wins", it means this order. *Why:* Claude Code's own order (local over project over user); round 2 Q4 asked for "which one wins".
- **D11 – Size and count limits:** a file over 1 MB is not parsed and gets the warning `Too large to read (over 1 MB)`; a folder lists at most 500 entries (then a `… <n> more` row in its section); folder recursion (`agents/**`, `commands/**`) stops at depth 5. Symlinks are followed only to regular files and folders; a broken one is skipped. *Why:* a home folder can hold anything; the page must stay fast.

### Sections

- **D12 – Overview:** one card per section (Plugins, MCP servers, Skills, Agents, Commands, Hooks, Memory, Permissions) with its count, split by source (`3 Project · 8 User · 4 Plugin`), clicking a card shows its section; then a **Warnings** list of every warning on the page (entry, file, message, Open file), or `No problems found`. *Why:* the item's "overview"; a place where every broken file shows.
- **D13 – Status:** a list of rows: **Claude Code**: its version and path, read by running `claude --version` and `command -v claude` through the user's login shell as the installed-agents check does (`bikube-found` marker, the profile's output ignored), or `Not installed` (the read is done when the page opens and on Refresh, never on the periodic refresh); **Account**: `oauthAccount.emailAddress` and `oauthAccount.organizationName` from `~/.claude.json`, or `Not signed in`; **Model**: the effective `model` setting, or `Default`; **Output style**: the effective `outputStyle`, or `Default`; **Settings files**: each of the four settings files and `~/.claude.json` and `.mcp.json` with `Found`, `Missing` or `Invalid` (with the parse error) and Open file; **Bikube hooks**: `Active in Claude Code cards`, and `Claude Code status: On`/`Off` from Bikube's Settings (`Claude Code status`). *Why:* developer's answer (round 2 Q5).
- **D14 – Stats:** for the workspace's folder plus the folder of every worktree card in the workspace (its worktree), from the Claude Code transcripts in `~/.claude/projects/<encoded folder>/*.jsonl` (`<encoded folder>`: the folder's absolute path with every character outside `A–Z a–z 0–9` replaced by `-`), plus each session's subagent transcripts as #50 reads them, over the last 30 days ending today (local dates):
  - a bar chart of **tokens per day** (input + output + cache write + cache read, #50's counts and its deduplication of streamed entries), with **sessions per day** (a session counted on the day of its first timestamped entry) as a second series; the hover tooltip and an accessible table give each day's numbers;
  - **Tokens by model**: one row per model (`model` of the counted entries), its share as a bar, its total;
  - **Most used**: three top-10 lists counted from `tool_use` blocks in assistant messages: **Tools** (by `name`), **Skills** (the `Skill` tool's `input.skill`), **Subagents** (the `Task` or `Agent` tool's `input.subagent_type`);
  - totals above the chart: sessions, tokens, and the folders counted (`3 folders`, tooltip listing them).
  No cost anywhere. Entries without a valid timestamp are skipped. Stats are read when the section is first shown and on Refresh only, never on the periodic refresh (D26), with `Reading sessions…` meanwhile; with no transcript in the period it reads `No Claude Code sessions in the last 30 days`. *Why:* developer's answers (round 1 Q8, round 2 Q10); #50: Bikube estimates no cost.
- **D15 – Plugins:** an **Installed** list: one row per installed plugin (`<name>@<marketplace>` key of `installed_plugins.json`) with its name, marketplace, version, description, author, and what it provides (`2 skills · 1 agent · 3 commands · hooks · 1 MCP server`, each count linking to its section filtered by the plugin), and an on/off switch for this workspace: on when the effective `enabledPlugins[<key>]` (D10) is `true`. A plugin whose `installPath` is missing gets the warning `Install folder missing`. Then a **Marketplaces** list, read-only: each known marketplace's name, its source (`github: <repo>`, a git URL or a path) and its last update. *Why:* developer's answer (round 2 Q8).
- **D16 – MCP servers:** one row per server: its name, type (`stdio`, `http` or `sse`), its command with arguments or its URL (environment variable and header values never shown, only their names), its source (`Project` for `.mcp.json`, `Local` and `User` for `~/.claude.json`, `Plugin <name>`), and its state. Project servers have a switch for this workspace: off when listed in the effective `disabledMcpjsonServers`, on when listed in `enabledMcpjsonServers` or `enableAllProjectMcpServers` is true, else `Not approved yet` (Claude Code asks at its next start) with the switch off. `Local` and `User` servers read `Enabled` and have no switch; a plugin's servers follow their plugin's switch. No server is ever started or connected to. *Why:* developer's answers (round 2 Q6, Q7).
- **D17 – Memory:** the memory files Claude Code loads for `<folder>`, in its load order: `~/.claude/CLAUDE.md` (User); `CLAUDE.md` and `CLAUDE.local.md` in every ancestor folder of `<folder>` from the root down (Project, the folder shown relative to `~` when inside it); `<folder>/CLAUDE.md`, `<folder>/.claude/CLAUDE.md`, `<folder>/CLAUDE.local.md` (Project or Local). Each row shows the file, its size and line count, and the files it imports (`@path` lines outside code blocks, paths relative to the importing file or starting with `~/`, followed up to 5 hops) nested under it; an import that doesn't exist gets the warning `Imported file not found`. Missing files are not listed. Expanding a row shows its first 40 lines as plain text. *Why:* developer's answer (round 1 Q4).
- **D18 – Skills, Agents, Commands:** one row per file: its name (a skill's frontmatter `name`, else its folder; an agent's frontmatter `name`, else its file name; a command `/<path:with:colons>`, plugin ones as `/<plugin>:<name>`), its frontmatter `description` (two lines, full text in the tooltip), an agent's `model` and `tools` as chips, a command's `argument-hint`, and its source. A plugin's entries show dimmed with `Plugin off` while its plugin is off. Warnings: `No frontmatter` (a skill or agent without a leading `---` block), `Invalid frontmatter` (not parseable as simple `key: value` YAML lines), `Missing name` or `Missing description` (skills and agents). Entries cannot be turned off one by one. *Why:* developer's answers (round 1 Q4, Q7).
- **D19 – Hooks:** grouped by event (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `SessionStart`…, in the order Claude Code documents, unknown events last by name), one row per hook command: its matcher (or `All`), the command (monospace, two lines, full text in the tooltip), its timeout if set, and its source; Bikube's rows carry the `Bikube` chip and no Open file. Warning `Command not found` when the command's first word is an absolute path, or starts with `$CLAUDE_PROJECT_DIR`/`${CLAUDE_PROJECT_DIR}` (taken as `<folder>`) or `${CLAUDE_PLUGIN_ROOT}` (its plugin's folder), and that file doesn't exist; other commands are not checked (no shell runs). A plugin's hooks show dimmed while it is off. *Why:* developer's answers (round 1 Q4, Q10).
- **D20 – Permissions:** read-only: `defaultMode` (effective, with its source), then **Allow**, **Ask** and **Deny** lists, each rule with its source, and `additionalDirectories`; empty lists read `None`. *Why:* developer's answer (round 2 Q9).
- **D21 – Config:** every top-level key set in the four settings files (Bikube's file excluded) other than those other sections show (`hooks`, `permissions`, `enabledPlugins`, `enabledMcpjsonServers`, `disabledMcpjsonServers`, `enableAllProjectMcpServers`), one row per key: the key, its effective value (D10), the file it comes from, and the other files that set it, struck through as overridden; `env` is shown as its variable names only. Then a **Preferences** group from `~/.claude.json`: its top-level booleans and numbers (no strings, objects or arrays), except keys that start with `num`, `has`, `last`, `cached` or `first`, or end with `At`, `Id`, `ID`, `Count` or `Cache` (runtime counters and caches, not preferences), read-only. *Why:* developer's answers (round 1 Q4, round 2 Q4); Claude Code ships no list of its `/config` options, so the page shows what is set rather than a list Bikube would have to maintain.
- **D22 – Editing config in place:** a settings key whose effective value is a boolean (a switch) or a finite number (a number field, saved on Enter or blur, refusing anything that isn't a finite number with `Enter a number`) can be changed; the change is written to `<folder>/.claude/settings.local.json` (D23), so it wins for this workspace, and the row then shows `Local` with the old file overridden. A row whose value comes from `settings.local.json` also has **Reset**, which removes the key from that file. Strings, arrays and objects are read-only (a wrong string can break Claude Code), and no new keys are added. `~/.claude.json` preferences are read-only. *Why:* developer's answer (round 2 Q4: booleans and numbers only).

### Changes and files

- **D23 – Writing settings.local.json:** the plugin switch (`enabledPlugins[<key>] = true|false`), the project MCP switch (adds the name to `enabledMcpjsonServers` and removes it from `disabledMcpjsonServers`, or the reverse) and D22's edits all write only `<folder>/.claude/settings.local.json`: main reads the file again just before writing, changes only that key, keeps every other key and the key order, writes 2-space-indented JSON with a final newline to a temporary file in the same folder and renames it over the file, creating `.claude/` and the file when missing. When the file exists but is invalid JSON nothing is written and the switch goes back, with the error line `Couldn't save: settings.local.json is not valid JSON`. Changes apply to Claude Code sessions started afterwards; the page says so once under its header after the first change (`Changes apply to Claude Code sessions started from now on`). *Why:* developer's answer (round 1 Q6); never overwrite a file the user is mid-way through editing.
- **D24 – Warnings:** invalid JSON in any JSON file (with the parser's message), D11's, D15's, D17's, D18's and D19's warnings. Each shows as an amber `⚠` on its row with the message, in the Overview's Warnings list and as its section's dot. A JSON file that doesn't parse contributes nothing else. *Why:* developer's answer (round 1 Q10).
- **D25 – Search:** one search box filters the rows of every section by name, description, command, URL, key or source (case-insensitive, every space-separated term must match); while it holds text each section's count reads the matching rows, and sections with none are dimmed; Esc in the box clears it. The query is kept per workspace for the run. Stats and Status are not filtered. *Why:* developer's answer (round 1 Q10).
- **D26 – Refresh:** everything but Stats and Status' Claude Code version is read when the page opens, again every 3 seconds while the page is in front and any Bikube window is focused (`anyWindowFocused`), at once on window focus, and on **Refresh**; never two reads at a time for one folder; a refresh keeps the section, scroll, search and expanded rows, and replaces only what changed. *Why:* developer's answer (round 1 Q10), as the Files tab (#55 D12).
- **D27 – Open file and Reveal:** every entry backed by a file (and each settings file in Status) has **Open file** (Settings > Editor, as the Files tab opens a file, with the file's folder as the project folder) and **Reveal** (the OS file manager showing the file, `shell.showItemInFolder`), as icon buttons shown on the row's hover and focus. Bikube's own hooks have neither. A failure shows the Files tab's error line (`Couldn't open <file name>: <reason>`). *Why:* developer's answers (round 1 Q5, Q10).
- **D28 – Main checks its input:** reading, writing, opening and revealing run in main, from the main frame only. A request names the workspace folder (an absolute, existing directory) and, for Stats, the extra folders (each absolute and existing; at most 100). Writes go only to `<folder>/.claude/settings.local.json` and only with a key and value of the kinds D22 and D23 allow (a plugin key that `installed_plugins.json` lists, a server name `.mcp.json` lists, a settings key whose current effective value is a boolean or number with a value of the same type). Open file and Reveal accept only a path that main's last read for that folder listed; anything else is refused and nothing runs. Main never runs a hook, an MCP server or anything a file names. *Why:* the renderer is sandboxed (#55 D16); the page must never become a way to open or write arbitrary paths.

## Data and migrations

None in `bikube-state.json`, `bikube-settings.json` or the sync file: the Agent setup view, its section and search are runtime only. Bikube writes only the workspace's `<folder>/.claude/settings.local.json` (D23), and only when the user flips a switch or edits a value.

## Out of scope

- Agents other than Claude Code (Codex, Gemini CLI, OpenCode, Pi).
- SSH workspaces (no remote reads).
- Managed (enterprise) policy settings.
- Installing, uninstalling or updating plugins, browsing marketplaces' plugins, adding marketplaces.
- Starting, connecting to or health-checking MCP servers; toggling `~/.claude.json` servers.
- Turning individual skills, agents, commands or hooks off; editing files in-app; adding new settings keys, editing strings, permissions rules.
- A per-worktree-card view of the setup (only Stats include worktree folders).
- Cost estimates.
- Card windows and a configurable shortcut for the page.
