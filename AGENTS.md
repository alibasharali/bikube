# AGENTS.md

Bikube: A kanban board for macOS and Linux where every card is a live terminal, for running many coding agents side by side.

Built with Software Factory's workflow: read `docs/agents/workflow.md` before starting on an item, and `docs/agents/stack.md` for the stack picked at creation and its guidelines. Domain terms are in `CONTEXT.md`, decisions in `docs/adr/`.

## Commands

- `npm ci` installs; `postinstall` rebuilds node-pty for Electron (needs python3, make and a C++ compiler on Linux). Where the Electron headers download is blocked (cloud sessions: postinstall fails with a proxy 403), everything else is installed by then: run `npm rebuild node-pty`; the Node build works in Electron too (N-API, ADR 0001). If `node_modules/electron/dist` is empty afterwards (the failed postinstall can skip Electron's own download), run `node node_modules/electron/install.js`.
- `npm run dev` starts the app with hot reload; `npm start` previews the production build. Both keep their data in `<appData>/bikube-dev` (`~/Library/Application Support/bikube-dev` on macOS), not the installed app's `bikube`, so they run beside it (`BIKUBE_USER_DATA_DIR` overrides).
- `.claude/check.sh` runs everything that must be green: typecheck, lint, Vitest, build, `node .factory/check-stack.mjs`. CI's `check` job runs it. Run as root (cloud sessions), the updater tests that make a folder read-only (`chmod 0555`) fail, since root writes it anyway: Vitest's "keeps the old app when its folder can't be written" and the smoke test "an install that can't swap the app". That is the sandbox, not the change; CI runs as a normal user. In cloud sessions the full smoke run (4 workers) can also time out restart tests (`panes.spec.ts` AC10, `ssh.spec.ts` AC3, `persistence.spec.ts` AC2), on `main` too: rerun them with `--workers=1` before suspecting the change.
- Individually: `npm run typecheck`, `npm run lint`, `npm test` (Vitest, with `SHELL=/bin/sh` from `vitest.config.ts`, so a developer's shell and its rc files never run in test PTYs), `npm run build`, `npm run format`.

## Architecture

- `src/main` Electron main process; `src/preload` the only bridge to the renderer, typed by `src/shared/api.ts` (`window.bikube`); `src/renderer` React UI; `src/core` plain TS with no Electron imports (session/PTY logic), unit-tested with Vitest on Linux.
- `board` (#9): inside a card's terminal (only there), an agent runs `board workspaces [--json]` (#69 D6: every workspace in sidebar order, `*` or `"current": true` on the calling card's, `workspacesListing`), `board list [--json]` (the calling card's workspace, or `--workspace`'s: its columns in order and their cards with id, title, running or stopped, activity, status, branch and a description flag, `src/core/board-list.ts`; the reply's `output` is printed to stdout), `board create [--agent <a>] [--description-file <f>|-] [--worktree [--branch <b>]] <column> <title>` (a card at the bottom of the column, not started, with the calling card's agent (`inheritedStartup`) or the target workspace's default; prints `<id> <workspace name>`), `board rename <card> <title>`, `board describe <card> <file>|-` (#69 D5: the CLI reads the file, `readDescriptionFile` in `src/core/description-file.ts`, and sends the text) (these four and `--workspace` local cards only: SSH cards' clients take `SSH_BOARD_USAGE`'s commands, and only local cards' `claude-instruction.txt` mentions them, `LOCAL_CLAUDE_INSTRUCTION`), `board move <card> <column>` (within the card's own workspace), `board status <card> <text>`, `board description <card>` (the SSH client takes it for its own card), `board activity <card> working|waiting|question|none` (#31: a pill on the card, runtime only, cleared on stop and start) or `board session <card> <uuid>` (run by Claude Code's hooks: the conversation the card resumes, saved); `board usage <card> <transcript>` (#50: not in `board help`, run by the Stop and SessionStart hooks; the local CLI reads the transcript, `src/core/claude-usage.ts`, and sends the token totals (no cost: Bikube estimates none); the remote client doesn't take it); a worktree card's setup line (#39) runs `board setup . ok|failed` (not in `board help`; only for the calling card, another card's reads `has no setup running`; `ok` clears the card's pending setup and types its start line) (`.` is the calling card; `board help`). Across workspaces (#69 D6, D7, D9): `--workspace <name or id>` (`resolveWorkspace` in `src/core/board-commands.ts`: an exact id, else a name in any case) picks the workspace for `list`, `create`, `rename`, `move`, `status`, `description` and `describe`; a card's id names it in any workspace (`resolveAnyCard`), titles only in the calling or named one; `activity`, `session`, `setup` and `usage` stay in the calling workspace; a session socket serves only its own card (`servesOwnCard`, `servesRemoteCard`). A request line is at most 512 KiB (`MAX_REQUEST_LINE_BYTES` in `src/core/board-protocol.ts`, room for a 100,000-character description); a new command needs its `FIELDS` and `parseRequestLine` there, `commandOf` in the relay and `answerBoardCommand` in the renderer. `resources/bin/board` (a POSIX sh wrapper; its directory is prepended to PATH in the environment of every card's shell and given as `BIKUBE_BIN`, so `"$BIKUBE_BIN/board"` works whatever a profile does to PATH) runs `out/main/board-cli.js` (built from `src/main/board-cli.ts`) with Bikube's own executable as Node; it talks to main over `<userData>/board/board.sock` (a private 0700 directory, the socket 0600), and main forwards each request to the renderer, which applies it to the store. Packaged, `bin/` is in `extraResources` and the CLI module and its chunks are unpacked from the asar (`electron-builder.yml`); after `npm run pack`, `dist/linux-unpacked/resources/bin/board` must be executable and `resources/app.asar.unpacked/out/main/board-cli.js` must exist. In SSH cards (#25) the local shell running `ssh` gets none of this: before each SSH session (main pane or extra pane) main listens on its own `<userData>/board/s-<16 hex>.sock`, serving only that card (`src/core/session-sockets.ts`), and the line becomes `ssh -o ExitOnForwardFailure=no -R /tmp/bikube-<32 hex>.sock:<that socket> -t -- …` (`src/core/ssh-command.ts`); the remote command writes a POSIX sh `board` script running an embedded perl or python3 client (`src/core/remote-board.ts`, no backslashes so it stays fish-safe) into a private `mktemp -d` directory and removes it and the remote socket when the shell ends. Claude Code cards (#31 D14) start `claude --settings "$BIKUBE_CLAUDE_SETTINGS"`: every card's shell gets `BIKUBE_CLAUDE_SETTINGS`, locally `resources/bin/claude-settings.json` (hooks calling `board activity`, and a SessionStart hook printing `claude-instruction.txt`); both files are generated from `src/core/claude-hooks.ts` and a test keeps them equal; the SSH remote command writes copies beside the remote `board` (the JSON's backslashes printed by `awk`, so the command keeps none). Session sockets close when their session exits and on quit; leftovers are removed at launch. Without a local socket ssh gets no `-R`, and the card runs anyway.
- Terminal themes: `src/core/ghostty-themes.json` is Ghostty's 463 theme files (iTerm2-Color-Schemes), rebuilt with `node scripts/import-ghostty-themes.mjs <ghostty>/themes`; "Use Ghostty theme" reads the user's Ghostty config in main (`src/core/ghostty-config.ts`). - Shell integration (#45): `src/core/shell-marks.ts` parses OSC 133, OSC 633 and OSC 7 and keeps a terminal's commands, prompts and last directory (`ShellMarks`, rows as an abstract line handle); every `XtermScreen` feeds it through xterm's parser like #58's probe (never swallowed, never answered), with rows as xterm markers (`screen.marks`), and marks a failed command with two decorations (`command-failed`, `command-failed-badge`) and the overview ruler, which is on at the scrollbar's own 14 px so fitting is unchanged. main reads the setting at each spawn; never the local shell running `ssh`): zsh gets `ZDOTDIR=<scripts>/zsh` (the user's kept in `BIKUBE_ZDOTDIR`), whose `.zshenv` puts it back, sources the user's `.zshenv` and loads `bikube-integration.zsh` (D the first precmd hook, A and B the last; at a prompt where hooks still follow it, such as the first, after a theme's in `.zshrc`, A and B go into PS1 from a one-shot `zle-line-init`, the user's own run first and put back, and `zle .reset-prompt`; put back only while `zle-line-init` is still Bikube's, so a widget a later hook defines or wraps it with stays, and Bikube's then only calls through); bash runs `--init-file <scripts>/bash/bikube.bash` instead of `-l`, which reads the login files itself, wraps PROMPT_COMMAND (string or array) and chains a DEBUG trap set before it, or, with bash-preexec loaded (starship, atuin; also when it shows up later, seen at the next prompt), hooks into its `precmd_functions`/`preexec_functions` instead and hands it the user's own trap (bash 3.2 syntax only, safe under `set -u`; `src/core/fixtures/bash-preexec.sh` is bash-preexec 0.5.0 for the test); bash is then not a login shell (`logout` refuses, `~/.bash_logout` doesn't run, a system bashrc may run twice; Shell integration off gives `bash -l`), and a line that is one whole subshell `( … )` runs no DEBUG trap, so from bash 4.4 its C and D go out late at the next prompt when the command number grew (the prompt's `\#` through `${…@P}`; never for an empty Enter), and before 4.4 it gets none; fish gets `<scripts>` first in `XDG_DATA_DIRS` (old value in `BIKUBE_XDG_DATA_DIRS`), whose `fish/vendor_conf.d` script restores it and wraps `fish_prompt` for B. Each script removes Bikube's variables and keeps `$?`/`$status` for the user's prompt and hooks. A new split (D8) tries the focused pane's last reported directory (`splitDirectory` in `src/core/shell-marks.ts`: a local absolute path, OSC 7's host empty, `localhost` or `os.hostname()`, which main passes the sandboxed renderer as an argument, `window.bikube.hostName`; never for SSH), and `CardPanes` spawns again in the card's directory when main refuses it. - Card windows (#53): the main window's page opens `about:blank` named `bikube-card:<card id>` (`src/renderer/src/card-windows.ts`) and draws the card view into that window's document with its own React root (`CardWindow.tsx`); main's open handler allows only that, from the main window (`cardWindowOpen`/`cardWindowOptions` in `src/core/card-windows.ts`, `src/main/card-windows.ts`), with no preload, so the window has no `window.bikube` and everything (sessions, acks, kept output, `board`, notifications) stays in the main page. Main keeps them by card id, focuses one on `cardWindow:focus` and closes them all when the main window closes, reloads or crashes; `appWindow()` (never a card window) is what a second launch, the global shortcut and macOS `activate` act on; the updater's and sync's messages reach every window, but only the main window's page listens. Code under the card view runs in the main page, so `window` and `document` are always the main window's: use `useViewWindow()` (`src/renderer/src/view-window.ts`) for keys, dialogs (`dialogOpenIn`), focus, sizes and `ResizeObserver`, never the globals, and a type check by `instanceof` fails across the realms. - Kept output (#46): a card's main pane only (never an extra pane or a shell), through the `OutputKeeper` `CardSessions` takes (`src/renderer/src/card-terminals.ts`'s `outputKeeper`): read before the spawn and written above a dim `── Previous output · <time> ──` line, saved with `@xterm/addon-serialize` (no modes, no alternate screen, as the `range` ending at the last row with text, so no final cursor moves: 0.14.0 has no `excludeFinalCursorPosition`) when the main pane stops and at `app:quitting`, trimmed to the Scrollback rows and 1,000,000 characters (`src/core/kept-output.ts`). - Terminal flow control (#16): main pauses a PTY above 100k characters the renderer hasn't acknowledged (`terminal:ack`, sent once xterm has parsed them) and resumes below 5k (`src/core/flow-control.ts`). Every chunk the renderer receives must be acknowledged exactly once (`SessionRouter` + `AckBatcher`), or its shell stays paused. node-pty drops a paused PTY's unread output 200 ms after its shell exits, so `SessionManager` resumes before kill and resumes a paused session whose shell is gone.
- Sync folder I/O (#26): never block main on the sync folder (it may be a stalled network mount or a cloud placeholder). `SyncFolder` uses async fs and runs every operation one at a time on its own queue, so a new operation must go through that queue to keep #13 D4 (no echo) and D12 (never overwrite). A libuv thread stuck in a stalled fs call keeps the process from exiting, so quit SIGKILLs main when sync is still busy at `quit` (`src/core/quit-hold.ts`).
